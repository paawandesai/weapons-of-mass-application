# Interview scheduling

How times proposed by a recruiter become a booked interview, and why nothing reaches the recruiter or the calendar before the user confirms. The rules are numbered as in [docs/design/wave3-inbox.md](design/wave3-inbox.md) (8, 9, 10, 11; 6 and 7 for compensation and booking links).

## Flow

1. **Offer**, in two halves (`apps/worker/src/scheduling/offer.ts`). Called by the inbox sync with `{userId, applicationId, threadId, messageId, slots, compensationFlag}` for an interview-classified message.
   - `recordOffer(handle, input, deps)` runs inside the caller's message transaction and sends nothing. Options marked ambiguous, options with no explicit UTC offset, unparseable or inverted ranges and options that start at or before now are dropped, each with a note. A missing end becomes start plus 60 minutes. The rest are checked against the user's primary calendar (Calendar freebusy, any overlap removes the option; touching at an edge does not). Nothing left: a `digest_flag` entry with `kind: "no_free_slot"` (reason, the conflicting ranges, the notes); no interview row, no email. Otherwise one `interviews` row per thread and one `interview_slots` row per option with a token (32 random bytes, base64url; only the sha256 is stored; 7 days on the database clock), all committing or rolling back with the message. It returns the raw tokens (`issued`), which exist only in memory and in the email.
   - `sendOfferEmail(handle, interviewId, deps, issued?)` runs after that transaction commits: ONE email to the user through `sendEmail` with a `${WEB_ORIGIN}/confirm/<token>` link per slot and the delivery key `slot_confirmation:<interview>:<first slot>`, then `confirmation_email_sent_at`. A blocked or uncertain send does not set it. Nothing is written to the recruiter.
   - `offerSlots` is the two calls in a row, for callers without a transaction.
   - An empty option list (a booking link, a request for availability) writes and sends nothing; the digest items for those come from the inbox sync.
   - A calendar that cannot be read logs `calendar_read_failed` and throws `CalendarUnavailableError`; nothing is stored or sent, and the caller retries on the next sync. A Google authentication error (401, `invalid_grant`, no grant) is rethrown unchanged so the connection is marked revoked rather than deferred forever.
   - Slots that cross a DST transition show both ends with their zone and offset ("1:30 AM PDT (GMT-7) to 1:30 AM PST (GMT-8)"), in the email, the reply and the confirm page.
2. **Confirm** (`apps/api/src/routes/confirm.ts`, public). `GET /confirm/:token` renders company, role, the time in the user's zone and a form with a POST button; it never writes (mail scanners prefetch links). `POST /confirm/:token` resolves the tenant from the token hash, then runs `confirmSlotByTokenHash` (one transaction: token unused, not invalidated, unexpired, slot not yet started on the database clock, interview not yet confirmed; the other tokens of the interview are invalidated; `confirmed_generation` is incremented), logs `slot_confirmed` and hands two jobs to the queue: `schedule-reminders` (so the reminders exist even if the recruiter reply is blocked) and `book-interview` (singleton key interview id and slot id). A used, expired, started or replaced link is `410` with the current state. A token that is malformed, unknown, or belongs to another tenant finds nothing. Each hand-off is independent; a failed one logs `book_enqueue_failed` and the repair pass queues booking again.
3. **Book** (`bookInterview`, run by the `book-interview` job behind the approval guard). The `book-interview` queue is created with the exclusive policy (`BOOK_QUEUE_OPTIONS` in `packages/shared/src/queues.ts`, used by both the worker and the API), so a singleton key excludes a duplicate while one is queued or running.
   - A confirmed slot that has already started (clock check) is not booked: `interview_booking_expired`, no reply, no event.
   - Schedule the reminders (backup for the confirm route; a failure is logged as `reminder_schedule_failed` and does not stop the reply).
   - Reply on the recruiter thread with the acceptance template (the time and the role only), once. The interview row is locked (`select ... for update`) while the reply context is read and the reply is sent, and every write is conditioned on the `confirmed_generation` read at the start; a reschedule or a newer confirmation either waits for this step or makes the booking return `stale`. The reply carries the delivery key `recruiter_reply:<interview>:<slot>`, written as a pending receipt before Gmail is called; a retry after a crash finds a sent receipt under that key and records `reply_sent_at` instead of sending again, and a pending one of unknown outcome throws `ReplyUncertainError` rather than risk a duplicate. A recruiter subject that quotes pay is replaced by a neutral subject.
   - Create the Calendar event with a client-generated id (32 hex characters) persisted in `calendar_event_client_id` BEFORE the insert; the Google port is get-or-create by that id, so a lost response or a crash retries the same event. After a reschedule the existing `calendar_event_id` is updated instead. If the call fails (other than authentication) `interview_event_failed` is logged and `EventCreationError` is thrown; pg-boss retries (5 times, backoff) and the retry skips the reply. An authentication error is rethrown unchanged and the job marks the connection revoked.
   - Move the card to Interviewing with `applyTransition` (`packages/db`, application row locked, `nextStatus` computed on the stored status, conditional update) and log `interview_booked`. `booked_generation` is set to the confirmed generation last; it is what marks this generation complete.
4. **Reschedule** (rule 11). New times on a thread whose interview is confirmed go through step 1 again: the open slots are replaced, `confirmed_slot_id`, `confirmed_at`, `reply_sent_at` and `confirmation_email_sent_at` are cleared and `confirmed_generation` is incremented (so a booking still in flight for the old time fails its writes); `calendar_event_id` and the old times are kept. The event is untouched until the user confirms a new slot; the booking job then replies again and updates the same event.

## Crash gaps

- Slots stored but the email not sent: `resendPendingConfirmations(handle, userId, deps)` re-checks the calendar, replaces the open slots with fresh tokens (tokens exist only in the email) and sends the request. The inbox sync calls it each hour.
- Slot confirmed but the booking job not queued, or booking not finished for the current generation: `requeueUnbookedInterviews(handle, userId, enqueue)` lists confirmed interviews that have not started and whose reply is not recorded or whose `booked_generation` differs from `confirmed_generation`. A retained event id from an earlier time does not count as done, so a reschedule whose Calendar update failed stays in the queue until it succeeds.

## Never

- No booking link is opened, and no reply or event exists before a confirmation.
- Compensation questions are never answered; the acceptance template has no money text and the guard in `sendEmail` still runs over it.
