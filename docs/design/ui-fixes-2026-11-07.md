# UI fixes, 2026-11-07

Six fixes Andre asked for after using the app. Each item names the behaviour, the files, and the
contract where the web and the API meet. Nothing here changes what the agent does; only how the
user sees it.

## 1. Runs page: positions link to the source

`apps/web/src/pages/RunViewPage.tsx`. Every candidate row already carries `url`. The title becomes
a link to that URL, opened in a new tab (`target="_blank" rel="noopener noreferrer"`). Rows
without a URL (empty string) keep plain text.

## 2. Progress bar while the profile is building

Today the build status is only `idle | running | done | failed`; the review page shows one
static line. The worker now records which phase a running build is in and the page draws a
determinate progress bar.

Phases, in order, recorded on the `profile_builds` row in a new nullable `step` text column
(migration `0018`): `gathering` (reading the connected sources), `extracting` (the model call),
`checking` (post-validation and saving). `runProfileBuild` sets the step before each phase when it
was given a `buildId`; the write is a plain `UPDATE ... WHERE id = $1 AND state = 'running'` and is
never part of the final transaction. A null step means `gathering`.

API contract (`GET /api/profile/build/status`, `BuildStatus` in `packages/shared/src/api.ts`):

```ts
interface BuildStatus {
  state: 'idle' | 'running' | 'done' | 'failed';
  version?: number;
  reason?: string;
  /** Running only. */
  step?: 'gathering' | 'extracting' | 'checking';
  /** Running only: when the build was reserved, ISO 8601. */
  started_at?: string;
}
```

Web (`ProfileReviewPage.tsx`): while a build runs (first build or rebuild) the banner holds a
`<progress>` with `max=3` and `value` 0 for `gathering`, 1 for `extracting`, 2 for `checking`,
plus a label per step: "Reading your sources", "Extracting your profile", "Checking it against
your sources". The polling loop already exists; it only has to keep the latest status in state.

## 3. The first run starts itself when the profile is approved

`POST /api/profile/approve`. When the approval is the user's first (their
`approved_profile_version` was null before), the route requests today's run exactly as the
"Run today" button does (`requestRun` in `apps/api/src/services/discovery.ts`, trigger `manual`),
best effort: a failure to start the run is logged and never fails the approval, mirroring how
`POST /api/survey` starts the first build. Re-approving, or approving a later version, starts
nothing. `approveProfileVersion` returns `first_approval: boolean` so the route can tell.

Response gains `run_started: boolean` (true when a run was handed to the worker). The review page
shows "Profile approved. Your first run has started." with a link to `/runs` when true, and the
existing "Profile approved." otherwise.

`createProfileRoutes` takes an optional `runQueue` for tests, next to the existing `queue`.

## 4. Connections page: saves confirm and collapse

`apps/web/src/pages/ConnectionsPage.tsx`. Every source card follows the same pattern: when the
source is connected, the card shows what is saved and a small "Change" control; the editor
(form, dropzone, folder picker) is hidden until the user asks for it, and hides again after a
successful save. The existing green notice ("Drive folders saved.") stays as the confirmation.

- Resume: connected shows filename and time (already there) and a "Replace" button that reveals
  the dropzone.
- LinkedIn and GitHub: connected shows the saved value and "Change"; the form is shown when not
  connected or after "Change".
- Drive folders: the server stores `config.folders` as `{ id, name }[]` next to `folder_ids`.
  Connected with folders shows the folder names and "Change folders"; otherwise the picker's
  "Choose folders" button as today. After a save the page reloads `me` so the names appear.

## 5. Loading and busy states

Web only. Two rules:

- Anything that waits on the network says so: a shared `Loading` component
  (`apps/web/src/components/Loading.tsx`, `role="status"`, text "Loading…" so existing tests keep
  passing, plus a CSS spinner) replaces every bare `<p className="muted">Loading…</p>`.
- Every button that triggers a request is disabled and relabelled while it is in flight:
  "Saving…", "Uploading…", "Starting…", "Disconnecting…". This covers the Connections forms and
  picker, the resume upload, `ConfirmButton` (an `onConfirm` that returns a promise keeps the
  group visible and disabled until it settles), and "Run today" on the Runs page.

## 6. Flagged items: "Go to field" works

`ProfileReviewPage.tsx`. Flags point at an entry (`work_history.0`), not a field, while inputs
are ids of fields (`f-work_history.0.start_date`), so the anchor never matched. Fix: give every
entry `fieldset` the id `f-<listKey>.<index>` and make the link resolve its target at click time:
the element with id `f-<path>` if it exists, otherwise the first element whose id starts with
`f-<path>.`. Scroll it into view and focus the first focusable control inside it. Flags with
several `paths` (date conflicts) get one link per path, labelled by the entry's title. Flags with
no path show no link, as today.
