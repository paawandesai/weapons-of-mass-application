# Application submission

How a pending application becomes a submitted one: the job, its states, ATS accounts, the CAPTCHA chain and the HTTP surface. The rules are numbered as in [docs/design/wave2-submission.md](design/wave2-submission.md). The generic form layer and the vendor hints are described in [submission-adapters.md](submission-adapters.md); the rules below are summarised in 'The generic submitter'.

## Pipeline

The daily run writes the `jobs` and `applications` rows (status `pending`) and enqueues `submit-application` with the application id as singleton key. The consumer is `apps/worker/src/jobs/submit-application.ts`; the attempt itself is `runSubmission` in `apps/worker/src/submission/job.ts`.

| Step | Activity entry | What it does |
|---|---|---|
| claim | `submission-started` | Per-application advisory lock for the whole attempt, then `for update skip locked` on the row. A row that is not `pending`, or that another attempt holds, logs `duplicate_enqueue` and nothing else happens. |
| adapter | `unsupported-ats` | The posting URL must belong to an Ashby, Greenhouse or Lever board. Decided before any browser is opened. |
| prior check | `submitted` with `prior: true` | On a retry, Gmail is searched for a confirmation that arrived after the first attempt started. If an earlier attempt got as far as `submitting`, the vendor page is loaded and checked for its confirmation marker, and the confirmation email gets the rest of its 600 s window, before anything is filled or submitted again. Either one moves the row straight to `applied`. A confirmation email counts only when its parsed sender is the company's own domain, or the ATS and the message names the company, and it mentions the job title. |
| tailor | `tailored` | Truthful resume rendered to `tenants/<tenant>/applications/<id>/resume.pdf`; the reference and the unmet requirements go on the row. |
| account | `account-created` or `account-signed-in`, `account-verified` | Only when the form requires an account (see below). |
| fill | `form-notice`, `filled` | A visible application-limit notice on the form (Ashby: "may not apply more than 5 times in any 180 day span") is recorded as `form-notice` with the numbers and does not stop the submission. The resume is attached first, then the form is filled, rescanned and verified: a required question whose value did not stick is `unmapped-field`, before anything is submitted. Every resolved value is written to `applications.form_answers`, keyed by question text, in the same transaction as the `filled` entry and before `submit`. Self-identification fields are never filled and are recorded as `{"skipped": "self-identification"}`. Yes/No facts (sponsorship, authorization, and relocation willingness questions, which come from the survey's willing-to-relocate answer; other relocation questions, such as assistance, go to the model) map onto the field's Yes/No options by meaning, and "authorized to work" is only answered Yes for a place the profile's work authorization covers. Consent acknowledgements on checkbox, radio and select fields (privacy policy, terms, data processing, accuracy of the application, and a label or description asking to review or confirm an AI policy or AI guidelines) are answered Yes by rule and recorded in `form_answers` like any other answer. Grouped checkboxes take the chosen option strings. Questions the profile cannot answer by rule go to the model, which sees identity, work history, projects, skills, education, preferences and the non-financial survey answers (relocation, career direction, work-life balance); never the salary floor or family constraints. |
| submit | `submitting`, `captcha-*` | A CAPTCHA before or after the click goes through the chain below. A submit button that is disabled after the fill is `unmapped-field` naming `submit`. Validation errors on the page after the click are `form-rejected`. |
| confirm | `submitted` | The vendor's confirmation marker on the page (selector or URL), else a generic thank-you text on the page, else a Gmail poll (every 15 s, up to 600 s) for a message from the ATS or company that mentions the job title. |

Each state change and its activity entry commit in one transaction, so a crash leaves the last entry as the evidence. One browser runs per worker process; each application gets its own context, closed in `finally`. At most two applications run at once per process.

## States and retries

`pending -> applied | pending(reason) | closed(submission-failed)`.

Pending reasons: `tailoring-check-failed`, `unsupported-ats`, `unmapped-field`, `missing-profile-field`, `unanswerable-question`, `verification-timeout`, `credential-rejected`, `captcha-timeout`, `unconfirmed`, `browser-error`, `form-rejected`. `form-rejected` (the vendor page showed validation errors after submit; the error texts are in the activity detail) is in the shared `PendingReason` enum like the others. It is not retried within the attempt. A failure sets the reason, increments `attempt_count`, stores `failure-<n>.png` when a page was open and logs the reason as the entry's action. The next daily run re-enqueues the row once without re-judging; a second failure closes it with `closed_reason = submission-failed`. `unsupported-ats` is never retried and never closed by the count. A deleted job closes the row with `job_missing`.

On `applied`, a `follow-up` job is enqueued with the application id as the job id and `startAfter = applied_at + 7 days`, and `applications.follow_up_enqueued_at` is set. An applied row with that column null is the outbox record: `reconcileFollowUps` (worker startup, then hourly) enqueues it, and the singleton key makes a repeat a no-op. Its consumer belongs to the inbox work.

Failure details in the activity log hold an allowlisted error category and a sanitized message (everything from the first mention of a password or token is dropped, URLs and long token-like runs are replaced). Raw browser text is never stored. A failure with no recorded outcome (database outage, profile load) is rethrown so pg-boss retries the job with the options in `SUBMIT_QUEUE_OPTIONS`.

## The generic submitter

One page layer reads, fills and submits any hosted ATS form from the accessibility semantics of the page, so a vendor redesign does not break selectors. Vendor files only hint (below). The numbered rules are in [design/wave5-generic-submitter.md](design/wave5-generic-submitter.md); in short:

- **Form root.** The nearest common ancestor of the resume file input (else the first visible text input) and the submit button; failing that, the first `form` with a visible control, else `body`. Site search, banners, headers, account forms, CAPTCHA widgets, dialogs, autofill uploaders and `aria-hidden` content are not questions.
- **Questions.** Every visible `input`, `select`, `textarea`, `[role=combobox|listbox|radio|checkbox|switch]`, pressed or `data-option` button and `contenteditable` is a control (file inputs count even when hidden). Radios, checkboxes and pressed buttons that share a `name` or a labelled box are one question whose options are their own labels; the Yes/No pair of buttons is a radio question with options `Yes`, `No`. Ids are the group `name`, else the control `id`, else `name`, else `q<index>` by document order.
- **Labels.** `label[for]`, `aria-labelledby`, `aria-label`, the group's own label or first text (legend, heading, a label whose target does not exist), a wrapping label, then the placeholder. Trailing `*`, `✱`, `(required)` and `(optional)` are stripped. Action texts such as "Attach" are not labels.
- **Descriptions.** A question's help text (`aria-describedby` targets, else a nearby element whose class contains `description`, `help` or `hint`, else the box text between the label and the control; at most 1,000 characters, never the label or the options) is `FieldDescriptor.description` and is sent to the answer model inside the `<question>` JSON, so a question like "confirm by selecting Yes" is answered with its instructions in view.
- **Required.** `required`, `aria-required`, a trailing asterisk in the label (also in an `aria-hidden` span), a `required` class on the label or box, or a hidden `input[required]` twin (react-select).
- **Kinds.** Text-like inputs and textareas are filled; native selects are chosen by label, then value, then ignoring case; comboboxes are opened (the menu may live in a portal; the options read are those of the active control, found through `aria-controls`/`aria-owns`, the react-select ids derived from its input id, or the nearest listbox that appeared after the click) and read once; more than 60 options, in a combobox or a native select, is `hint: large-list` with the options omitted, and such a question is filled by typing (combobox) or by the option whose text contains the value (select), a required one with no match being `unmapped-field`. After typing, the generic layer waits for the refreshed results rather than acting on the old rows. An autocomplete without options is typed into and its first containing option chosen; Yes/No buttons, radios and checkbox groups are chosen by option label; dates are typed in the placeholder format (default `MM/DD/YYYY`), a `start_date` date question never parks and takes the profile's `standard_answers.earliest_start_date` (an ISO date set on the review page), else a date derived from the start-date text or notice period ("within N days", "immediately" = +14 days, "N weeks notice"), else today + 30 days, weekends rolling to Monday, while a text start question keeps the `start_date` text; a phone number in an international phone widget is typed as national digits once the widget's country is set. An unrecognised control is `text` with `hint: unknown-control`.
- **Prior-contact questions.** "Have you worked at / interviewed at / applied to <company> before?" is answered Yes or No from facts the system holds: `work_history` employers for "worked"; the profile's `standard_answers.previous_interviews` (a list of company names, edited on the review page as a comma-separated list; `[]` means none) for "interviewed"; for "applied", an earlier applied application for that company or a name in `previous_interviews`. The company is the one the question names, else the posting's company, compared after dropping case, punctuation and suffixes such as Inc. Work-authorization wording also covers "permanent authorization to work", "eligible to work" and "legally able to work".
- **Inferred defaults (rule 28).** A required standard question whose profile value is null is answered with a default, recorded in `form_answers` as `{value, source: 'inferred'}`: work authorization from the country in `identity.location` or the phone code (else the country the question names; none derivable parks as `missing-profile-field`), no sponsorship needed when authorization was inferred, `previous_interviews` as none, start date "Within 30 days", notice period "2 weeks", relocation No for a remote preference, Yes when the posting's location is in `preferences.locations`, else No. An explicit profile value always wins; optional questions are left blank.
- **Educated guesses (rules 28-30).** Following Andre's policy change, a question the profile does not state outright is not a reason to stop. The answer prompt has a guess mode: when the profile makes one answer clearly more likely (years with a listed skill, a tool in the same family, team size from a highlight) the model answers it with `guessed: true` and `grounded: false`, the ungrounded retry does not fire, and the answer is filled with source `guessed` (the options and length checks still apply, with their one retry). It never guesses credentials, licences, certifications, clearances, criminal history, compensation, demographics, legal attestations beyond work authorization, or a hard requirement the profile contradicts, and a required question with no defensible guess is still `unanswerable`. Inferred standard answers and guessed free-text answers are stored in `applications.form_answers` as `{value, source: 'inferred' | 'guessed'}`, shown on the application card with "Answered by inference, correct it in your profile if wrong", and listed in the daily digest under "Answers we guessed today". A profile edit that fills the field stops the inference.
- **Settled page.** A React page is visible before it is interactive. After the form appears, `load` waits for network idle (8 s at most), then rescans until one scan's stamped elements all survive 500 ms (10 s at most). Any later step that finds a stamped element missing rescans once before acting. Anonymous controls (no id, no name) get a structural id (`q:<label>:<tag/type>`, plus their position among the same in their box), so inserting a control elsewhere does not renumber them; a combobox's value is read only from its own shell (a selected-value element or hidden backing input), never from the text left in its search box, and values are compared whole, so a truncated phone number or a country that is a prefix of another does not verify. Before submit the final scan is audited: any required question still empty, including one an earlier answer revealed, is `unmapped-field`.
- **Verification.** After the fill the page is rescanned and every filled question is compared with its intended value; a required one that did not stick is `unmapped-field` with the failure screenshot, before submit.
- **Submit and outcome.** Inside the root: a `button[type=submit]`, else a button reading Submit, Apply or Send application. Within 10 s of the click: the vendor confirmation, else the form gone (no visible native or role-based control left in it) and a thank-you text that appeared after the click (text already on the page before it is never evidence), else visible validation errors, including ones that were already showing before the click and are still there (`form-rejected`), else a CAPTCHA, else `unconfirmed` and the Gmail wait.
- **Stepped forms.** Sections marked `data-step` are walked with Next/Back for the fill and the submit.
- **CAPTCHA.** Besides the text-and-image widget, an hCaptcha or reCAPTCHA challenge iframe (visible, with size) or a visible `[data-sitekey]` box is a CAPTCHA. It has no image to read, so it skips both solver stages and goes straight to the human stage with a full-page screenshot. An invisible reCAPTCHA badge alone is not a CAPTCHA. A completed challenge keeps its frame on the page, so completion is read from the response token (`g-recaptcha-response`, `h-captcha-response`) or the frame being hidden. The frame handle's `enter` does nothing (the challenge is in a cross-origin frame); it is cleared only when the provider marks it solved.

## ATS accounts

When `requiresAccount` is true the job looks up `ats_credentials` for the user, ATS and company. The whole operation runs under an advisory lock on (user, ATS, company). A `verified` credential signs in; a rejected sign-in (or a vault entry that is missing or corrupt) sets `rejected_at` and parks the application as `credential-rejected`. Accounts are never recreated automatically. Without a credential, a 24-character password is generated, written to the vault (`ats_password`, reference `<ats>:<company_id>`) and to `ats_credentials` with status `registering`, and only then is the sign-up submitted. A credential still `registering` (the worker died mid-sign-up) is resumed with its vaulted password: the sign-up is submitted again, and if the vendor refuses it a sign-in with the same password completes it; a refused sign-in there is not final. If the page still asks for an account afterwards, Gmail is polled every 15 s for up to 300 s for a verification link or a 6-8 digit code from mail received after that credential's registration started and tied to the company (same rule as confirmation mail); no mail in time is `verification-timeout`. Success marks the credential `verified`. Passwords never reach logs, activity entries or the application row.

## CAPTCHA chain

`findCaptcha` returns a handle; for a text-and-image widget the job stores the image, inserts a `captcha_requests` row at stage `agent1` and logs `captcha-detected`.

1. `agent1`: up to three attempts with the `solve-captcha-a` prompt.
2. `agent2`: up to three attempts with the `solve-captcha-b` prompt (different instructions, no shared history).
3. `human`: one open request per user (a second one is parked at once with `captcha-parked` and the application is `captcha-timeout`). A single-use token is generated; only its sha256 is stored. The user gets an email through `sendEmail` with the image inline and a link to `${WEB_ORIGIN}/captcha/<token>`. The worker polls the row every 5 s. A wrong answer sends a fresh image and token (three human attempts at most) inside the same 900 s window, measured from the first email. At the end of the window the context closes, `expired_at` is set and the application is `captcha-timeout`.

An iframe challenge (`challenge: 'frame'`) skips stages 1 and 2: the request is logged with a `captcha-stage` entry from `agent1` to `human` and the user gets the same email with a full-page screenshot. A frame has no text field, so a reply cannot be typed into it; the stage ends in `captcha-timeout` unless the challenge clears on its own.

The row records the resolving stage and the attempt count per stage; both appear in the application detail.

## HTTP

| Route | Purpose |
|---|---|
| `GET /api/applications?status=pending,applied` | The signed-in user's applications, newest first. |
| `GET /api/applications/:id` | Detail: job, resume reference, form answers (question, status, value), unmet requirements, activity, CAPTCHA summary with stage and attempts. |
| `GET /captcha/:token` | The reply form with the challenge image. Public: the token is the credential. |
| `POST /captcha/:token` | Stores the reply when the request is open (unanswered, unresolved, unexpired). Otherwise 410 "no longer open" and nothing is written. |

## Configuration

`WEB_ORIGIN` (links in the CAPTCHA email), `FILE_STORE_DIR` (images, resumes, screenshots), `VAULT_MASTER_KEY`, `ANTHROPIC_API_KEY`, and the user's Google connection with Gmail read and send access.

## Tests

```bash
scripts/db-test-reset.sh
pnpm -F @wma/worker test
pnpm -F @wma/api test
pnpm -F @wma/worker exec vitest run test/submission/e2e.test.ts
```

The last command runs the three vendor forms end to end against the saved fixtures (it needs Playwright's Chromium). `test/submission/generic.test.ts` scans the real captures in `apps/worker/test/fixtures/forms/real/` and drives one synthetic page per control kind in `forms/generic/`; `generic-job.test.ts` covers `form-rejected`, `form-notice` and the iframe CAPTCHA path. The CAPTCHA round trip through the reply page is `apps/api/test/captcha-e2e.test.ts`.
